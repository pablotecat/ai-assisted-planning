# User stories

Treat a story as a prompt for a conversation about a user or purchaser outcome, with confirmation of what success means. Use the branches that fit the request:

1. Identify what is supplied: beneficiary and goal, source of the claim, planning horizon, related work, known constraints, and any agreed checks. Mark consequential gaps and distinguish facts from inference. If the work's form is unclear, use [principles](references/principles.md). **Done when:** each fact needed for the decision is supplied or explicitly unknown.
2. To turn an idea into a candidate, use [drafting](references/drafting.md). To diagnose or reshape an existing item, use [reviewing](references/reviewing.md). Use both when a review calls for a supported rewrite. **Done when:** each requested outcome has a candidate, finding, or stated reason to defer.
3. When meaning of done, exceptions, vague qualities, or cross-cutting rules matter, use [confirmation](references/confirmation.md). When estimates, priorities, iteration boundaries, external interfaces, or team coordination matter, use [context](references/context.md). Read only the applicable sections. **Done when:** each relevant branch has been applied and any unsettled decision has an owner.
4. Return the proposed item or verdict with its intended value and the reason for each material change. Separate supplied/agreed decisions from suggestions; show consequential open questions with the person who can resolve them. If actor and outcome cannot be grounded, return a pending proposal and focused questions. **Stop when:** every material recommendation follows from supplied evidence or is labeled provisional, every proposed check is distinguishable from an agreed one, and the requester can tell what to adopt and what a human still must decide.
